## 1. 目指す体験

### 主催者

「2分以内に候補を作り、安心してリンクを配り、回答の重なりから迷わず確定できる」

### 回答者

「ログインを強制されず、1分以内に回答でき、自分の回答だけを安全に直せる」

### リピーター

「過去のイベント、よく使う時間帯、自分の予定を再利用し、毎回の入力を減らせる」

## 2. プロダクト原則

1. 1画面1判断
2. 共有前に結果を予測できる
3. 誰が何を変更できるかを隠さない
4. 入力は保存し、失敗しても失わせない
5. ログインは必須条件ではなく、反復利用の価値として提示する
6. 色やアニメーションより、状態と次の行動を先に伝える
7. データ収集は必要最小限とし、利用者へ説明できるものだけにする

## 3. 体験別の改善案

### 3.1 イベント作成

現行:

```text
イベント情報 -> 入力方式 -> 条件 -> 手動選択? -> 確認
```

提案:

```text
目的を選ぶ / 空から作る
  -> 候補条件
  -> 候補プレビュー
  -> タイトルと共有設定
  -> 作成完了 + 回答リンク / 管理リンク
```

プリセット例:

- 30分の会議
- 1時間の会議
- 平日夜の練習
- 土日のイベント
- 終日の候補日
- 自由に設定

プリセットは候補を自動入力するだけで、利用者が内容を確認・変更できる。

重要な変更:

- 「自動 / 手動」という実装都合より、「早く作る / 細かく選ぶ」という成果で表現する。
- 条件変更と同時に「6日 × 5枠 = 30候補」のような結果を表示する。
- 確認画面で参加者が見る回答画面をプレビューする。
- 作成完了で「回答リンク」と「管理リンク」を明確に分ける。

### 3.2 回答

改善案:

- 最初にイベント名、回答締切、候補数、所要時間を表示。
- 名前入力後すぐ候補へ進み、ログイン提案は回答完了後へ移す。
- 曜日一括入力は実在する候補枠だけを操作可能にし、適用件数と非適用理由を即時表示。
- 既存の390px対応を維持し、回答表と主要操作が画面幅内に収まることを回帰テストで固定。
- ○ / △ / × の三値を検討。
- PCはドラッグ、モバイルはタップと範囲選択を中心にする。
- 「すべて○」「平日夜だけ○」など安全な一括操作と取り消しを提供。
- 未送信変更を明示し、離脱時に下書きをローカル保存。
- 送信後に専用の回答編集リンクを表示し、コピーを促す。

### 3.3 集計と確定

改善案:

- 最上部に「全員参加できる候補」「あと1人で全員」「未回答者」を表示。
- ヒートマップ、候補ランキング、参加者別詳細をタブまたは段階表示に分ける。
- 確定前に影響を明示:
  - 選択日時
  - 回答人数
  - 未回答者
  - 確定後の編集可否
- 確定時に回答者へ送る共有文を生成。
- 回答締切、回答ロック、確定取り消し履歴を主催者だけに提供。

### 3.4 履歴とアカウント

改善案:

- 匿名初回:
  - URL / IDから開く
  - 新しく作る
- 匿名再訪:
  - 最近のイベントを最上部
  - ログイン同期は補助 CTA
- ログイン済み:
  - 進行中 / 回答待ち / 確定済み
  - 自分が作成 / 回答した
  - 次に必要な操作

空状態では空のセクションを複数並べず、最も起こりやすい次の行動を1つ強調する。

### 3.5 信頼

各イベントで表示:

- このリンクで見える情報
- 回答を見られる人
- 確定できる人
- データ保持期間
- 作成者への連絡方法
- 最終更新

管理リンクを持つ主催者には:

- 変更履歴
- 管理リンク再発行
- 回答締切
- イベント削除
- データエクスポート

## 4. フェーズ

### Phase 0: 信頼性の穴を塞ぐ（1〜2週間）

対象:

- 曜日一括入力を実候補へ正しく反映し、存在しない曜日・時間を操作不可にする
- `maximumScale: 1` を削除
- エラー画面の問い合わせ先修正
- `GUEST` / ログイン文言修正
- Jestの `act(...)` 警告を解消
- 想定エラーログをテスト内で明示的に扱う
- `answer-wizard.md`、Motion、PWA文書のずれを修正
- 未使用依存を削除
- `date-fns` へ統一する計画を確定

完了条件:

- lint / typecheck / test / build 成功
- test stderr に想定外警告なし
- 390 / 768 / 1280、ライト / ダークの主要画面目視完了
- 回答者情報から回答完了まで、390 / 768 / 1280px で横方向のページスクロールなし
- 曜日一括入力の選択数と日付別確認の反映数が一致
- エラー画面から実際の問い合わせ先へ到達

### Phase 1: 境界を作る（2〜4週間）

対象:

- Zod と共通 Action result
- `event-create` を feature 化
- 作成ウィザードを reducer ベースへ変更
- イベント作成の rate limit / idempotency
- 構造化ログと request ID
- Storybook + a11y addon の最小導入

完了条件:

- `actions.ts` から create use case を分離
- 作成 action の不正入力 / 大量候補 / 二重送信テスト
- Button、Field、Progress、Dialog の主要状態を Storybook 化
- axe の重大違反0

### Phase 2: 権限と共有を再設計（不採用の履歴）

2026-08-13のプロダクト判断により、以下は実装しない。

対象:

- organizer capability
- 回答 / 管理リンク分離
- 回答公開範囲
- 締切とロック
- capability 再発行 / 失効
- 既存イベント互換

完了条件:

- 公開リンクだけでは候補変更 / 確定不可
- 既存リンクは移行方針に従って継続利用可能
- 管理リンク紛失時の復旧手段あり
- 権限マトリクスのRLS / RPC / E2Eテスト完了

### Phase 3: 中心体験を短くする（3〜5週間）

対象:

- 作成プリセット
- 候補数ライブプレビュー
- 回答所要時間と締切表示
- 回答下書き
- 集計ランキング
- 未回答者と確定前確認

完了条件:

- 初回作成の中央値2分以内
- 回答の中央値1分以内
- 主要操作がモバイル1画面1判断
- 作成 / 回答の中断復帰が可能

### Phase 4: 差別化機能（検証後）

候補:

- ○ / △ / ×
- Google / Outlook カレンダーの空き時間取り込み
- 候補ごとの会場 / オンラインURL
- リマインダー
- 繰り返しイベント
- 投票締切の自動確定補助
- 参加者向けタイムゾーン表示

カレンダー連携は必ずサーバー側 OAuth、最小 scope、明示同意、解除導線を前提にする。

## 5. ライブラリ導入判断

| ライブラリ / 機能                        | 推奨度 | 導入箇所                                 | 理由                                                    |
| ---------------------------------------- | ------ | ---------------------------------------- | ------------------------------------------------------- |
| Zod                                      | 高     | 全 Server Action 入口                    | 型、長さ、配列、相関条件を一元化                        |
| React `useActionState` / `useFormStatus` | 高     | 単純フォーム                             | Next.js標準の pending / error / progressive enhancement |
| Conform                                  | 中     | 作成フォームで試行                       | Server Action と Zod の連携、エラー関連付け             |
| React Aria Components                    | 中〜高 | DatePicker、Dialog、Tooltip              | キーボード、ラベル、locale の実装負担削減               |
| `@internationalized/date`                | 中     | 日付UI                                   | 壁時計時刻とlocaleの扱いを明示                          |
| Storybook + addon-a11y                   | 高     | 共通UIと複雑状態                         | 状態網羅とa11y回帰防止                                  |
| axe-core / Playwright連携                | 高     | 主要E2E状態                              | ページ単位の自動a11y検査                                |
| fast-check                               | 中〜高 | 日付変換、候補生成、状態遷移             | タイムゾーン・境界値・操作順の組合せを性質ベースで検証  |
| Sentry / OpenTelemetry                   | 中〜高 | Server Action、RPC、画面エラー           | request ID、失敗率、遅延、経路追跡                      |
| XState                                   | 保留   | 回答フローがさらに複雑化した場合         | 現時点では reducer を先に試す                           |
| TanStack Query                           | 保留   | 高頻度クライアント再取得が必要な画面のみ | 全体導入はServer Componentsと重複                       |
| motion                                   | 低     | モーダル、成功 / 失敗の状態変化だけ      | 装飾目的では不要                                        |

曜日表・日付表は、ドラッグ選択、タッチ抑制、固定時間列、390px圧縮について長い改善履歴とテストがある。React Aria の `Grid` へ一括置換せず、まず既存表へ行・列を含むアクセシブル名、フォーカス移動、axe / キーボードテストを追加する。置換は同等操作を小さな検証画面で証明できた場合だけ行う。

削除候補:

- `framer-motion`: ソース利用0件
- `motion`: ソース利用0件
- `lodash`: ソース利用0件
- `axios`: ソース利用0件
- `dayjs`: calendar APIだけで利用。`date-fns` 系へ統一後に削除

削除前に `git grep`、ビルド、E2Eで再確認する。

## 6. 計測設計

### North Star

`7日以内に、作成されたイベントが1件以上の回答を得て確定される割合`

単なる作成数ではなく、日程が決まったかを測る。

### ファネル

```text
create_started
  -> create_method_selected
  -> create_previewed
  -> create_completed
  -> share_clicked
  -> first_response_received
  -> event_finalized
```

回答:

```text
response_started
  -> availability_edited
  -> response_reviewed
  -> response_submitted
```

### 測る値

- 作成完了時間
- 回答完了時間
- ステップ別離脱率
- バリデーションエラー率
- 自動 / 手動の選択率
- 候補数分布
- 共有操作率
- 初回回答までの時間
- 確定までの時間
- 再試行成功率
- モバイル / デスクトップ差
- 匿名 / ログイン差

### 収集しない値

- イベントタイトル本文
- 参加者名
- コメント
- 生のURL / token
- 候補日時そのもの

イベントIDは不可逆ハッシュまたは短命な分析IDにする。
