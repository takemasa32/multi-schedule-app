# 過去の実装意図と今後の継承方針

> **2026-08-13 決定:** 全員同一権限は見直さず、現行の単純な公開リンク運用を継承する。organizer capability、管理リンク、権限分離は導入しない。以後の性能・UX改善は [見た目・使い勝手を維持する性能 / UX 改善方針](performance-ux-preservation-plan-2026-08-13.md) に従う。

作成日: 2026-07-29

## 1. 目的

現行実装を根本から改善する際に、過去の判断を「古いから削除する」「複雑だから単純化する」と短絡的に扱わないための判断台帳である。

以下を区別する。

1. 現在も守るべき意図
2. 当時は合理的だったが、成長段階の変化で見直す意図
3. 後続実装ですでに置き換えられた意図
4. 意図は正しいが、実装が複雑化して保守コストだけが増えた領域

## 3. 判断の時系列

### 2026-01: 権限を単純化

`68c9095` で管理者概念を廃止し、公開リンクを知る全員を同じ操作権限として扱う方針へ変更した。

当時の狙い:

- 主催者・参加者の権限分岐をなくす。
- 既存DB変更を最小化する。
- 共有リンクだけで回答から確定まで進められるMVPを優先する。
- 将来拡張用に `admin_token` は残す。

評価:

- MVPの単純化として一貫している。
- 公開リンクだけで回答、集計、確定まで進められる単純さを、現在もプロダクト価値として優先する。
- `admin_token` は既存互換のため残すが、権限分離には利用しない。

結論:

- 全員同一権限を継承し、入力検証、濫用制限、処理の冪等性で運用品質を高める。

### 2026-02: 回答をウィザード化

回答者情報、曜日一括入力、日付別確認、確認・送信へ段階化した。

当時の狙い:

- 1画面に集中していた入力を分け、入力ミスと離脱を減らす。
- ログイン利用者の予定を初期値へ反映し、反復入力を減らす。
- 未ログイン回答を維持する。
- 旧 `list / table` 切替を廃止し、曜日表と日付表へ操作を集約する。

評価:

- 段階化、ゲスト回答、二種類の表への集約は現在も有効。
- 候補が2件だけでも4ステップを通るなど、条件に対して固定ステップが重い。
- 曜日一括入力は実候補と一致する曜日・時間なら正しく反映される一方、実候補に存在しないセルも同じように操作可能で、適用対象外であることが分からない。

結論:

- ウィザードは維持し、候補数・認証状態・予定カバー率に応じてステップを省略する。
- 曜日一括入力は廃止せず、実候補限定の入力へ変える。

### 2026-02〜03: ログイン価値を回答前に強調

`7479fdb` で、利用者が「ログインせずに進む」を押した後にログイン確認モーダルを追加した。

当時の狙い:

- 回答履歴同期と次回自動反映の価値を伝える。
- ログイン回答を推奨しつつ、ゲスト回答は残す。

評価:

- 意図的に追加された導線であり、単なる重複実装ではない。
- 現在はLPで「回答はログイン不要」を強く約束しているため、回答開始時の二段確認は期待と競合する。
- 2026-05以降、回答完了後にアカウント保存を提案する専用画面が整った。

結論:

- ログイン価値の案内は残す。
- 回答開始前の再確認ではなく、回答完了後の任意保存・同期の文脈へ集約する案を検証する。

### 2026-03: 日程確定を専用ルートへ分離

`9d12cc4` で、イベント詳細内の折りたたみ確定UIを専用ルートへ移した。

当時の狙い:

- 影響範囲が大きい確定操作を、候補選択と確認へ分離する。
- 新規確定、解除、維持の差分を保存前に理解できるようにする。
- モバイルでも主要操作を維持する。

評価:

- ローカル正常系でも、選択、差分確認、最終確認が誤確定防止に寄与した。
- 1候補だけの場合は確認回数が多く感じるが、権限分離がない現状では安全側の価値が高い。

結論:

- 専用ルートと差分確認は維持する。
- 確認強度を調整する場合は、候補数と変更量だけを条件にし、権限差には依存しない。

### 2026-05: アカウント週予定を廃止

`c2f3ec0` で `user_schedule_templates` を削除し、アカウント予定を日付ごとの予定へ集約した。

当時の狙い:

- 永続的な週テンプレートとイベント回答の複雑な相互反映をやめる。
- アカウント予定は日付ごとの予定と確定イベント重複から計算する。
- 曜日一括入力は現在の回答だけに適用する。

評価:

- 回答画面の曜日入力をアカウントへ暗黙保存しない現行挙動は、この破壊的変更の意図に沿っている。
- 曜日一括入力を改善する際、週テンプレート保存を復活させると過去の複雑性を再導入する。

結論:

- 曜日入力はイベント内の入力補助として維持し、アカウントの永続予定モデルには戻さない。

### 2026-06〜07: 回答送信とマイ予定保存を分離

`03a4c1e` と `f34fc56` で、回答送信前の同期範囲モーダルを廃止し、回答完了後にアカウント保存を確認する形へ移した。

当時の狙い:

- 回答しただけでマイ予定が変わる逆方向保存を防ぐ。
- イベントへの回答成功を、他イベント同期の成否から切り離す。
- 利用者が明示的に保存した場合だけアカウント予定へ反映する。

評価:

- ローカル正常系で、ゲスト回答はイベントへ保存され、完了画面へ安全に遷移した。
- `answer-wizard.md` のStep4〜5は旧同期モーダルを説明しており、実装意図より文書が古い。

結論:

- 現行フローを維持する。
- 設計文書を現行の完了ページ方式へ更新する。

### 2026-07: 非LP UIを刷新

`5c4ed8b` ではURL、データモデル、Server Actions、認証、業務ルールを変えず、見た目と情報階層だけを刷新した。

当時の狙い:

- 紫、丸いバッジ、カードの入れ子、強い影を減らす。
- 主要操作だけを紫にし、実用画面の読み取りを優先する。
- 既存E2Eのラベルと `data-testid` を維持する。

評価:

- 現行画面の落ち着いた一貫性に寄与している。
- 権限や回答ステップが変わらなかったことは刷新範囲の制約どおりであり、見落としではない。

結論:

- 既存トークン、余白、状態色、共通パターンは次の改善でも継承する。
- 業務ルール変更とビジュアル変更は別PRで進める。

## 4. 継承・見直し・廃止

### 継承する

- 公開リンクを知る全員を同じ操作権限として扱う方針
- ログイン不要の回答
- Supabaseへのサーバーサイド接続
- Server Actions / RPCによる更新
- 回答送信とアカウント予定保存の分離
- 日程確定の専用ルートと差分確認
- 390pxで7日表を成立させる既存レイアウト
- 紫を主要操作と選択状態へ限定するデザイン方針
- 装飾目的のモーションを増やさない方針

### 見直す

- 回答開始前のログイン再確認
- 候補数に関係なく固定された回答ステップ
- 曜日一括入力と実候補の対応
- 過去イベントでも通常と同じ回答・確定・カレンダー導線
- 1,200〜1,600行級ファイルへ集約された責務

### 復活させない

- `user_schedule_templates` によるアカウント週予定
- 回答送信前の同期範囲モーダル
- クライアントからSupabaseへの直接接続
- 全画面への装飾モーション
- バッジ、グラデーション、カード入れ子を増やすだけの刷新

## 5. 今後のPRで使う判断基準

各PRは次の問いへ答える。

1. どの過去意図を維持するか。
2. どの前提が変わったため見直すか。
3. 利用者の操作回数、誤操作、待ち時間のどれを改善するか。
4. DB、権限、同期、既存イベントへどの互換影響があるか。
5. 390 / 768 / 1280px、キーボード、200%ズームでどう検証するか。
6. 仕様、設計、CHANGELOG、テストのどこを同時更新するか。

## 6. 直近の実装順

1. 曜日一括入力と実候補の対応を修正し、反映件数を表示する。
2. `answer-wizard.md` を回答完了後の保存確認方式へ更新する。
3. 回答 action とウィザード状態を feature 単位へ分離する。
4. 回答後の重複DB処理と日程確定後の逐次同期を削減する。
5. 過去イベントの `upcoming / finalized / completed / archived` 状態を設計する。
