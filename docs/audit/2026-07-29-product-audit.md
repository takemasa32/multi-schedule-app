# DaySynth 現行プロダクト総合監査

> **2026-08-13 方針更新:** プロダクト判断により、権限分離、管理リンク、organizer capabilityは導入しない。本文の権限所見は2026-07-29時点の監査記録として残すが、現在の実装優先度には使用しない。現行方針は [見た目・使い勝手を維持する性能 / UX 改善方針](../architecture/performance-ux-preservation-plan-2026-08-13.md) を正とする。

監査日: 2026-07-29
対象: `main` ブランチのローカル実装
監査モード: UX / UI / アクセシビリティ / 設計 / 保守性 / 運用品質の複合監査

## 1. 結論

DaySynth は「ログイン不要で候補を共有し、回答の重なりから決める」という中心価値が明確で、画面の見た目、Server Components 優先、RPC による一括更新、テスト量は良い水準にある。

一方、次の成長を阻む最大要因は見た目の細部ではない。

1. 公開リンクを知る全員に同じ変更権限を与える設計が、主催者の安心感を損ねる。
2. 複雑な画面と Server Actions が 1,200〜1,600 行級のファイルへ集中し、変更速度と回帰耐性が落ち始めている。
3. 作成・回答フローは段階化されているが、説明と進捗表示が多く、「いま決めること」が薄くなる場面がある。
4. サーバー入力検証、濫用対策、アクセシビリティ自動検査、プロダクト指標が不足している。

そのため、次の刷新は「新しい装飾を足す」より、権限・状態・入力・計測の土台を直し、その上で主催者と回答者の主要タスクを短くする順番が適切である。

## 2. 監査範囲と確認方法

- 画面:
  - トップページ
  - イベント作成のイベント情報、入力方式、候補条件
  - 履歴の空状態
  - イベント取得失敗時のエラー状態
- 表示条件:
  - デスクトップ
  - 390 × 844 のモバイル
  - ライト / ダークテーマ
  - WSL 上のローカル Supabase 正常系（デスクトップ）
- 実装:
  - `src/app`
  - `src/components`
  - `src/lib`
  - Supabase マイグレーションと RLS 方針
  - 単体テスト / E2E 構成
  - 既存の `/docs` と仕様書
- 実行確認:
  - `npx supabase start`
  - ローカル seed の取得
  - ゲスト回答の作成
  - 回答集計への反映
  - 日程確定と確定後表示
  - `npm run lint`
  - `npm run typecheck`
  - `npm run test:ci -- --runInBand`
  - `npm run build`

初回監査では `.env.local` が指す外部 Supabase へ到達できず、イベント取得失敗状態を確認した。その後、WSL で `npx supabase start` を実行し、監査用 Next.js サーバーだけをローカル Supabase へ接続して再監査した。ローカル seed のイベント取得、ゲスト回答、集計反映、日程確定まで完走し、DB でも「参加者2名・監査回答2枠・確定日程1件」を確認した。

## 3. 総合評価

以下は絶対評価ではなく、改善順序を決めるための相対的な診断である。

| 観点             | 状態                                                               | 評価   |
| ---------------- | ------------------------------------------------------------------ | ------ |
| 中心価値         | 「予定を重ねて決める」が一貫している                               | 良好   |
| ビジュアル       | ライト / ダークともに統一感がある                                  | 良好   |
| 作成 UX          | 段階化は良いが、情報密度と二重進捗が重い                           | 要改善 |
| 回答 UX          | 正常系とレスポンシブ表示は完走するが、曜日一括入力に混乱要因がある | 要改善 |
| 確定 UX          | 選択、差分確認、最終確認の安全性が高い                             | 良好   |
| 再訪 UX          | 履歴・お気に入り・URL入力が揃うが、空状態の優先順位が分散          | 要改善 |
| アクセシビリティ | ラベルやランドマークは良いが、ズーム制限と自動検査不足がある       | 要改善 |
| 信頼・権限       | リンク保持者が同一権限で変更できる                                 | 最優先 |
| 拡張性           | 巨大コンポーネント / 巨大 Action ファイルへの集中が進む            | 最優先 |
| テスト           | 62 suites / 357 tests が通過                                       | 良好   |
| テスト品質       | `act(...)` 警告や想定エラーの大量ログが残る                        | 要改善 |
| 運用・計測       | 技術ログはあるが、ファネルや成功時間の計測が弱い                   | 要改善 |

## 4. 画面フローと証拠

### Step 1: トップページ（デスクトップ・ダーク）— 良好

![トップページのデスクトップ表示](screenshots/2026-07-29/01-landing-desktop-viewport.png)

良い点:

- サービス名、価値、説明、主要 CTA、補助 CTA の順が明確。
- 「無料・広告なし・回答はログイン不要」が不安を早い段階で解消している。
- 概念図は「複数の予定が一つの候補へ集約される」ことを言葉なしでも補助している。

改善点:

- ヘッダーの `GUEST` は状態表示に見える一方、実際は Google ログイン操作であり、意味が一致しない。
- 主要 CTA とヘッダーの作成 CTA が同時に強く見え、初回画面内で操作が重複する。
- 「誰でも確定や編集ができる」という現行権限の重要な注意は、価値訴求から分からない。

### Step 2: トップページ（モバイル・ダーク）— 概ね良好

![トップページのモバイル表示](screenshots/2026-07-29/05-landing-mobile.png)

良い点:

- ファーストビュー内に価値、説明、CTA、無料 / ログイン不要が収まる。
- 画像を背景へ回すことで、縦長化を抑えている。
- 作成 CTA は横幅いっぱいでタップしやすい。

改善点:

- 背景画像と本文が重なるため、端末やテーマ差によっては本文コントラストが不安定になる。
- ヘッダーは「作成」「GUEST」「テーマ」の3操作が狭い幅に並び、サービスロゴより操作群の密度が高い。
- スクロール直後にブランドコンセプト説明が続き、リピーターが履歴へ戻るまでが長い。

### Step 3: トップページ（デスクトップ・ライト）— 良好

![トップページのライトテーマ](screenshots/2026-07-29/08-landing-light-desktop.png)

良い点:

- 白地、黒文字、紫 CTA の階層が素直で読みやすい。
- ヒーロー画像が装飾より補助情報として機能している。

改善点:

- ダークテーマより画像の存在感が弱く、右側が大きな余白に見える。
- ヘッダーのテーマボタンだけ輪郭が強く、作成 CTA と視覚的に競合する。

### Step 4: イベント作成・イベント情報（デスクトップ）— 概ね良好

![イベント作成のイベント情報](screenshots/2026-07-29/02-create-step1-desktop.png)

良い点:

- 必須 / 任意が明確。
- 1画面の入力項目が少なく、開始の心理的負担は低い。
- 次の操作が1つに絞られている。

改善点:

- ページ見出し、カード見出し、進捗、補助文が同時に表示され、入力2項目に対して説明量が多い。
- CTA がカード右下にあり、長い説明欄の後では視線移動が大きい。
- 保存されるタイミングや、途中入力が保持されるかが分からない。

### Step 5: イベント作成・入力方式（デスクトップ）— 要改善

![入力方式の選択](screenshots/2026-07-29/03-create-method-desktop.png)

良い点:

- 自動 / 手動の違いをカード単位で比較できる。
- ラジオとして意味付けされ、キーボード / 支援技術向けの土台がある。

改善点:

- 全体3段階と候補日程内2段階の進捗が同時にあり、現在位置を理解するための情報が二重。
- 各カード内の3文が意味的に重複する。「自動」「細かく手動」の一文と具体例で足りる。
- 未選択でも「次へ」が主要色で表示されるため、先に押してからエラーを知る流れになりやすい。
- おすすめがなく、初めての利用者は方式選択に迷う。既定を「かんたん作成」にし、高度な手動指定を後から選べる構造がよい。

### Step 6: イベント作成・候補条件（デスクトップ）— 要改善

![候補条件の設定](screenshots/2026-07-29/04-create-auto-settings-desktop.png)

良い点:

- 期間、時間帯、枠長のまとまりは自然。
- 00:00 の扱いを明示している。
- ヘルプ操作にアクセシブル名がある。

改善点:

- 日付、時刻、枠長のすべてを一度に理解する必要があり、ウィザード化の効果が弱まる。
- 「平日の夜」「土日の午後」「30分の会議」など、実際の目的から始めるプリセットがない。
- 日付入力とタイムゾーンの関係が見えない。参加者が異なる地域にいる場合に解釈がずれる。
- 生成される候補数のプレビューがないため、条件変更の結果を次へ進むまで想像しにくい。

![イベント作成のモバイル表示](screenshots/2026-07-29/06-create-step1-mobile.png)

良い点:

- 入力幅とタップ領域は十分。
- 1列レイアウトで破綻していない。

改善点:

- 進捗が縦3行になり、入力開始前に大きな高さを使う。

- モバイルでは画面下固定の「次へ / 戻る」操作と、キーボード表示時の安全領域対応を検討したい。

### Step 8: 履歴の空状態（デスクトップ・ライト）— 要改善

![履歴の空状態](screenshots/2026-07-29/09-history-empty-light-desktop.png)

良い点:

- URL / ID から戻れる逃げ道がある。
- ログインしなくても履歴画面を使える。
- 空状態の理由と、次にできる操作が書かれている。

改善点:

- ログイン、URL入力、お気に入り、イベント作成が同じ強さで並び、最優先の行動が不明。
- 「ログインすると同期」は機能説明に留まり、再訪や端末変更時の具体的な価値が弱い。
- 初回利用者に空の「お気に入り」と「履歴」を連続表示するより、最近のイベントを開く / 新しく作るの2択へ絞る方が短い。

### Step 9: イベント取得失敗（デスクトップ・ダーク）— 見た目は良好、復旧導線は要修正

![イベント取得エラー](screenshots/2026-07-29/07-event-fetch-error-desktop.png)

良い点:

- エラー、説明、再試行、トップへ戻るの順が明確。
- 色だけでなくアイコンと文言で状態を伝えている。

改善点:

- 「お問い合わせ」はコード上で `/terms` に遷移しており、期待する連絡先へ到達しない。
- ネットワーク失敗、イベントなし、権限なしをユーザーが区別できない。
- 再試行を連打した際のバックオフや状態説明がない。
- 開発環境ではエラーオーバーレイの Issue バッジが重なったが、これは本番 UI の評価対象外。

この画面は外部 Supabase へ到達できない実行条件で確認した依存障害時の状態であり、ローカル Supabase 接続後の通常状態ではない。

- 回答状況、共有、確定、候補追加、履歴が縦に連なり、イベント規模が大きくなるほど主要判断が埋もれる。

### Step 13: 曜日一括入力 — 要改善

![曜日ごとの一括入力](screenshots/2026-07-29-local-supabase/04-weekly-availability.png)

![曜日ごとの一括入力（390px）](screenshots/2026-07-29-local-supabase/13-weekly-availability-mobile.png)

良い点:

- 日程数が多いときに曜日パターンをまとめて入力できる発想は、回答時間を短縮できる。
- ○ / × と背景色が同時に変わり、選択結果が分かりやすい。
- 2025-06-11 と 2026-02-25 の幅調整・モバイル最適化の意図は現行でも機能している。1280px と 390px の双方でページ全体の横スクロールは発生せず、主要 CTA も画面幅内に収まった。
- 実候補と一致する「火曜10時、水曜15時」を選んだ再検証では、日付別確認へ正しく2件反映された。反映ロジックそのものではなく、適用対象外セルも同じ操作可能状態で見せることが問題である。

改善点:

- 実際に存在しない曜日・時間も選択できる。今回「月曜10時、火曜15時」を選んだが、実候補は「火曜10時、水曜15時」であり、次ステップへ期待どおり反映されなかった。
- 選択可能セルと実候補の対応を説明しないため、利用者は入力が消えたように感じる。
- 色と記号だけでなく「選択済み / 未選択」の読み上げ名、フォーカス表示、矢印キー操作を確認する必要がある。

推奨:

1. 実在する候補枠だけを曜日表で操作可能にし、存在しないセルは disabled とする。
2. 曜日一括入力後に「2件に適用されます」のような反映件数を即時表示する。
3. 回答件数が少ない場合はこのステップを省略し、日付別入力から始める。

![日付別の回答確認（390px）](screenshots/2026-07-29-local-supabase/14-date-review-mobile.png)

良い点:

改善点:

- 曜日一括入力で選んだ内容が反映されなかった理由が表示されず、再入力が必要になった。
- 390px では日付、曜日、時刻、状態がかなり小さくなる。現在の一画面比較を維持しつつ、200%ズームと実機タップ精度を別途確認する必要がある。

### Step 15: 送信確認と完了 — 良好

![回答内容の送信確認](screenshots/2026-07-29-local-supabase/06-submit-review-stable.png)

![回答完了](screenshots/2026-07-29-local-supabase/07-answer-complete.png)

### Step 17: 日程確定 — 良好

![日程確定の候補選択](screenshots/2026-07-29-local-supabase/09-finalize-selection-stable.png)

![日程確定の差分確認](screenshots/2026-07-29-local-supabase/10-finalize-review.png)

良い点:

### Step 18: 確定後のイベント — 良好

![確定後のイベント詳細](screenshots/2026-07-29-local-supabase/12-finalized-event.png)

良い点:

- 確定済みバッジ、確定日時、共有、Google カレンダー、ICS が上部へまとまる。
- 回答集計より先に最終結果を示し、再訪者が迷わない。
- DB でもイベント確定フラグと確定日程1件を確認した。

改善点:

- 過去日時でもカレンダー追加を強く案内する。過去イベントでは「開催済み」「再調整」「複製」を優先したい。
- Google カレンダーと汎用カレンダーの文言差が小さく、後者が ICS ダウンロードであることを補足すると分かりやすい。
- 回答更新が確定結果へどう影響するか、確定後回答のルールを画面上で説明する必要がある。

## 6. 実装品質の確認結果

| 確認                               | 結果                                 |
| ---------------------------------- | ------------------------------------ |
| ESLint                             | 成功                                 |
| TypeScript / route type generation | 成功                                 |
| Jest                               | 62 suites 成功、357件成功、1件 skip  |
| 本番ビルド                         | 成功                                 |
| ルート生成                         | 静的13ページ生成、動的ルート生成成功 |

強み:

- TypeScript strict、Server Components、Server Actions、Supabase RPC の方向性が揃っている。
- クライアントから Supabase へ直接接続しないことをテストで守っている。
- 日付、ヒートマップ、同期、RLS、エラー、テーマなど重要領域のテストが多い。
- 重いイベント詳細を `Suspense` で分け、同一リクエストのイベント取得を `cache()` している。

正常系の追加確認:

- WSL の Supabase CLI 2.84.5 と Docker Desktop 29.3.1 でローカルスタックを確認した。
- `npx supabase start` は成功し、既存 seed を再利用できた。
- ローカル API / DB を使う監査用サーバーからイベントを取得した。
- ゲスト回答を作成し、集計画面と DB の両方へ2枠が反映された。
- 1候補を確定し、確定後画面と DB の両方へ反映された。

注意:

- テスト成功と警告ゼロは別である。React の `act(...)` 警告が残る状態では、非同期更新の検証漏れを将来見逃しやすい。
- カバレッジ目標の達成可否は今回のコマンドでは再計測していない。
- ローカル Supabase は本番相当のセキュリティ構成ではない。正常系の機能確認には使えるが、TLS、rate limit、メール配信、外部認証、ネットワーク障害時の挙動は別環境で確認する。
- 送信・確定はローカル seed にのみ反映し、外部 Supabase と既存の `.env.local` は変更していない。
- 監査完了後、作成した監査参加者1名と確定日程1件を削除し、seed イベントを「参加者1名・未確定」の開始状態へ戻した。

## 7. アクセシビリティ所見

確認できた強み:

- `header`、`nav`、`main`、`footer` のランドマークがある。
- 入力方式は `radiogroup` / `radio` として公開されている。
- ヘルプ、テーマ、ログインなどアイコン操作にアクセシブル名がある。
- ステップ進捗には読み上げ用の現在 / 完了 / 未完了情報がある。
- `prefers-reduced-motion` 向けの全体ルールがある。

リスク:

- `maximumScale: 1` はピンチズームを妨げるため削除が必要。
- モバイルヒーローの画像上テキストは、画像差し替えやテーマ変更でコントラストが崩れやすい。
- ヒートマップとドラッグ選択は、スクリーンショットだけではキーボード同等操作、読み上げ順、状態通知を確認できない。
- 曜日・日付表は `button` / `switch` として公開されている一方、同名の ○ / × や「未選択」が多数並ぶ。行・列の文脈をアクセシブル名へ含める必要がある。
- 390px の通常表示では横幅崩れを確認しなかったが、200%ズームと400% reflowは未確認である。
- ウィザード遷移後のフォーカス移動とエラー時のフォーカス復帰は、実機キーボード / スクリーンリーダー確認が必要。
- 自動検査がないため、今後の変更でラベルやコントラストの回帰を止められない。

この監査は WCAG 適合を保証しない。axe、キーボード、VoiceOver / NVDA、200%ズーム、400% reflow、色覚差の手動確認が別途必要である。
